# Rubric: is this plan ready to post and build from?

All dates and versions are measured against the bundle's capture date in eval mode, and against today in live mode. Maintainers are users with OWNER, MEMBER, or COLLABORATOR badges.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis | **Live (`gh` / draft):**<br>`gh issue view {issue} -R {owner}/{repo} --json title,body`<br>Candidate `plan.md` "Diagnosis" section and repro comment on the issue<br><br>**Eval (bundle):**<br>"Diagnosis" in Candidate plan read against Issue description and "Repro evidence" block | Passes if the plan says what causes the bug and provides the evidence to support the diagnosis in agreement with the issue title (diagnosis is relevant to the issue) and grounded in the reproduction evidence. FAILS if the diagnosis contradicts the reproduction steps or control runs, ignores the defect mechanism, or chases an adjacent symptom or workaround rather than the actual cause. | required |
| scope | **Live (`gh` / draft):**<br>`gh issue view {issue} -R {owner}/{repo} --json title,body`<br>Candidate `plan.md` "Scope" section<br><br>**Eval (bundle):**<br>"Scope" and "Files" in Candidate plan read against Issue description and "Repro evidence" block | Look where the plan says what it will change: passes if it names each file it will change and says what it won't touch, providing reasoning for what the changes are for. FAILS if the plan exhibits scope creep by bundling unrelated drive-by refactorings, architectural redesigns, unnecessary dependency updates, or extra features beyond what is required to resolve the reported defect. | required |
| changes | **Live (`gh` / draft):**<br>Candidate `plan.md` "Files" and "Approach" sections; working tree diff<br><br>**Eval (bundle):**<br>"Files", "Approach", and "Proposed changes" sections in Candidate plan | Identifies which files are being modified and why. If changes involve adding or deleting files or code blocks, it must justify why adding or deleting. Changes should be minimal (targeting under 500 lines) and concrete enough that an unfamiliar engineer can execute them without deferring design or implementation decisions to build time. | required |
| test | **Live (`gh` / draft):**<br>Candidate `plan.md` "Test plan" section and test runner commands; repro comment steps<br><br>**Eval (bundle):**<br>"Test plan" in Candidate plan read against "Steps" and artifacts in "Repro evidence" block | Passes if the plan adds a test. The plan specifies an automated test (unit or integration) or deterministic reproduction re-run that directly asserts the defect's resolution against an observable, verifiable outcome. FAILS if the plan merely proposes running existing test suites without defining a specific, observable pass/fail condition that proves the fix resolved the defect. | required |
| contribution-policy | **Live (`gh` / draft):**<br>`gh issue view {issue} -R {owner}/{repo} --json comments`<br>`gh api repos/{owner}/{repo}/contents/CONTRIBUTING.md`<br>Candidate `plan.md` and draft plan comment<br><br>**Eval (bundle):**<br>"Thread highlights" and "contribution policy" under Repo facts read against Candidate plan and plan comment | The plan and candidate submission comply with the repository's stated contribution guidelines (`CONTRIBUTING.md`) AND do not contradict or violate any explicit direction, constraints, or guidance maintainers put forward in the issue thread. FAILS if the plan ignores or contradicts maintainer instructions in the thread, or violates stated repository contribution rules. | required |
| risks-and-tradeoffs | **Live (`gh` / draft):**<br>Candidate `plan.md` "Deviations", "Risks", or "Trade-offs" sections<br><br>**Eval (bundle):**<br>Stated risks, unknowns, or trade-offs in Candidate plan or Candidate plan comment | The plan explicitly acknowledges known risks, checked unknowns, performance considerations, or intentional trade-offs rather than claiming false certainty. | preferred |

## Verdict rule

READY (accept) only if every required check passes (`diagnosis`, `scope`, `changes`, `test`, `contribution-policy`). Preferred checks (`risks-and-tradeoffs`) never change the verdict and serve only to rank plan quality. Any FAIL or UNCLEAR on any required check results in HOLD (reject): a plan whose cause is ungrounded, scope is unbounded, changes are vague, test is unobservable, or submission violates maintainer thread direction or contribution guidelines must not be posted upstream or built from.
