# Rubric: is this plan ready to post and build from?

All dates and versions are measured against the bundle's capture date in eval mode, and against today in live mode. Maintainers are users with OWNER, MEMBER, or COLLABORATOR badges.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis | `evidence-guide.md` → Diagnosis and grounding | Passes if the plan says what causes the bug and provides the evidence to support the diagnosis in agreement with the issue title (diagnosis is relevant to the issue) and grounded in the reproduction evidence. FAILS if the diagnosis contradicts the reproduction steps or control runs, ignores the defect mechanism, or chases an adjacent symptom or workaround rather than the actual cause. | required |
| scope | `evidence-guide.md` → Scope | Look where the plan says what it will change: passes if it names each file it will change and says what it won't touch, providing reasoning for what the changes are for. FAILS if the plan exhibits scope creep by bundling unrelated drive-by refactorings, architectural redesigns, unnecessary dependency updates, or extra features beyond what is required to resolve the reported defect. | required |
| changes | `evidence-guide.md` → Executability | Passes only if both conditions hold. **(1) The design is decided:** the plan says what the change does (the rule, check, or mechanism it adds, removes, or alters) and makes every choice between alternatives now. **(2) The change is located:** it names each file it will modify, add, or delete, with the reason for each, and justifies any addition or deletion. Naming a module or code path instead of exact functions still meets (2) if the plan says how it will pin down the exact place (for example, a trace or debug log it already has working). Changes should target under 500 lines. FAILS (1) if any design choice is left to build time (for example "I'll pick an approach while implementing" or "option A or option B, to be decided"). FAILS (2) if no files or code paths are named. Leaving exact function names to be found does not fail on its own when (1) holds. | required |
| test | `evidence-guide.md` → Test plan | Passes if the plan adds a test. The plan specifies an automated test (unit or integration) or deterministic reproduction re-run that directly asserts the defect's resolution against an observable, verifiable outcome. FAILS if the plan merely proposes running existing test suites without defining a specific, observable pass/fail condition that proves the fix resolved the defect. | required |
| contribution-policy | `evidence-guide.md` → Comms and Contribution Policy | The plan and candidate submission comply with the repository's stated contribution guidelines (`CONTRIBUTING.md`) AND do not contradict or violate any explicit direction, constraints, or guidance maintainers put forward in the issue thread. FAILS if the plan ignores or contradicts maintainer instructions in the thread, or violates stated repository contribution rules. ALSO FAILS if the stated policy requires disclosing AI assistance in issues or comments and the plan comment does not disclose it; treat every plan as AI-assisted. A disclosure rule that applies only to pull requests does not apply to a plan comment. | required |
| risks-and-tradeoffs | `evidence-guide.md` → Honesty | The plan explicitly acknowledges known risks, checked unknowns, performance considerations, or intentional trade-offs rather than claiming false certainty. | preferred |

## Verdict rule

READY (accept) only if every required check passes (`diagnosis`, `scope`, `changes`, `test`, `contribution-policy`). Preferred checks (`risks-and-tradeoffs`) never change the verdict and serve only to rank plan quality. Any FAIL or UNCLEAR on any required check results in HOLD (reject): a plan whose cause is ungrounded, scope is unbounded, changes are vague, test is unobservable, or submission violates maintainer thread direction or contribution guidelines must not be posted upstream or built from.
